# TeleDrive — Implementation Plan

Companion to [REQUIREMENTS.md](REQUIREMENTS.md). This describes **how** each phase gets built, in order.

---

## Key Technical Decisions

| Area | Decision | Reason |
|---|---|---|
| Framework | React 18 + TypeScript + Vite | Fast dev server; one codebase for web and mobile |
| Telegram | GramJS (`telegram` npm package) | Runs in browsers, full MTProto (2 GB uploads) |
| Node polyfills | `vite-plugin-node-polyfills` | GramJS expects `Buffer`, `crypto`, etc. |
| Styling | Tailwind CSS | Quick, consistent UI; easy dark mode |
| State | Zustand | Small, simple global store |
| Local DB | Dexie (IndexedDB) | Session, file index cache, sync state |
| Routing | React Router | `/login`, `/drive/*`, `/settings` |
| Mobile | Capacitor | Wraps the same web build into Android/iOS |
| Tests | Vitest | Unit tests for metadata, index, chunking |

### Metadata design (caption JSON)

Folders are **ID-based**, not path-based, so renaming or moving a folder edits **one** message instead of every file inside it.

```jsonc
// Folder marker message (text message)
{"td":1,"t":"d","id":"k3j9","p":"root","n":"Photos"}

// File, part 1 (document message): holds all the metadata
{"td":1,"t":"f","id":"a8f3","p":"k3j9","n":"beach.jpg","s":4821930,"m":"image/jpeg","of":1,"ts":1759200000}

// File, parts 2..N (document messages): just a pointer back to the file
{"td":1,"t":"c","id":"a8f3","pt":2}
```

| Key | Meaning |
|---|---|
| `td` | Format version (lets us migrate later) |
| `t` | Type: `d` folder, `f` file (part 1), `c` extra chunk |
| `id` | Random short ID (nanoid) |
| `p` | Parent folder ID (`root` = top level) |
| `n` | Name |
| `s` / `m` | Size in bytes / MIME type |
| `of` / `pt` | Total parts / this part's number |
| `ts` | Created timestamp |
| `x` | Flags added later (e.g. `"tr":1` trash, `"fav":1`, `"enc":1`) |

Captions are limited to **1024 characters**, so keys stay short. Names longer than ~900 characters are rejected.

A **config message** (`{"td":1,"t":"cfg",...}`) is pinned in the channel. It holds drive-wide settings (format version, and later the encryption salt).

### Sync strategy
1. **First load:** read the whole channel history with `messages.getHistory` in pages of 100, parse the captions, save to Dexie.
2. **After that:** `updates.getChannelDifference` using the stored `pts` returns only new, **edited**, and **deleted** messages since the last sync.
3. **Live:** listen to GramJS update events while the app is open.
4. **Fallback:** if the difference is too long (Telegram says so), do a full rescan.

### Rate limits
- GramJS `floodSleepThreshold` auto-waits on short `FLOOD_WAIT` errors.
- Transfer queue: max 2–3 concurrent chunk transfers.
- Bulk operations are batched (e.g. `deleteMessages` 100 at a time).

## Phase 1: Core Drive (MVP)

### 1.1 Login
- `auth.ts`: `sendCode(phone)` → `signIn(code)` → if `SESSION_PASSWORD_NEEDED`, `checkPassword(2fa)`.
- Save the `StringSession` to Dexie; restore it on startup, then go straight to the drive.
- Handle errors: wrong code, expired code, `PHONE_NUMBER_INVALID`, `FLOOD_WAIT` (show a countdown).
- Logout: `auth.logOut`, clear Dexie.

**Done when:** you can log in, refresh the page, stay logged in, and log out.

### 1.2 Storage channel
- Search your dialogs for a channel whose config message has `"t":"cfg"`.
- If none exists: `channels.createChannel` ("TeleDrive Storage", private), post and pin the config message.
- Store the channel ID and access hash in Dexie.

**Done when:** the first login creates the channel (visible in your Telegram app), and later logins reuse it.

### 1.3 Metadata + tree (pure logic, unit-tested)
- `meta.ts`: `encode(item)` and `decode(caption)`, validation, the 1024-character check.
- `tree.ts`: messages → `{folders, files}` maps; `children(folderId)`, `breadcrumbs(folderId)`, `isDescendant(a, b)` (prevents moving a folder into itself).
- Messages with a missing or invalid caption are ignored (so other posts in the channel don't break anything).

**Done when:** Vitest tests pass for encode/decode, tree building, orphan handling, and the move-into-self guard.

### 1.4 Sync
- Full scan → Dexie → Zustand.
- Incremental sync with `getChannelDifference` on app start and every 30 s while the app is visible; live updates via events.

**Done when:** a file uploaded on one browser appears in another browser within about 30 s.

### 1.5 Upload
- Split the `File` with `Blob.slice` into 512 MB chunks. GramJS internally uploads each chunk in 512 KB parts.
- Upload part 1 with the full metadata caption, then parts 2..N with `"t":"c"`.
- Progress = bytes sent / total. Cancel = abort, then delete any parts already sent.
- Multiple files at once through `queue.ts`; drag-and-drop with `UploadDropzone`.
- Send with `forceDocument: true` so Telegram doesn't compress photos and videos.

**Done when:** a 5 MB photo and a 2.5 GB file (3 chunks) both upload with progress and appear in the list.

### 1.6 Download
- Fetch the parts in order with `downloadMedia` / `iterDownload`, with progress.
- Save:
  - **Chrome/Edge:** File System Access API (`showSaveFilePicker`), streaming chunks straight to disk, so any size works.
  - **Other browsers:** build a Blob and trigger a download (warn above ~1 GB).

**Done when:** the downloaded files are byte-identical to the originals (check the SHA-256 of the 2.5 GB test file).

### 1.7 File operations
| Operation | Implementation |
|---|---|
| New folder | Send a folder marker message |
| Rename | Edit the caption of the folder marker or of file part 1 |
| Move | Edit `p` in that caption (block moving a folder into itself) |
| Delete file | Delete all its part messages |
| Delete folder | Collect all descendants, then delete in batches of 100 |

Name conflicts in the same folder are auto-renamed to `name (1).ext`.

### 1.8 UI
- Layout: sidebar (Home, Settings), top bar (breadcrumbs, search box placeholder, view toggle), main area.
- Grid and list views, sorting (name/date/size/type), file-type icons.
- Right-click / long-press menu: Download, Rename, Move, Delete, Details.
- Transfer panel (bottom-right): active uploads/downloads with progress, pause, cancel.
- Stats in the sidebar: file count and total size.
- Responsive from the start (works at phone width), because the same UI becomes the mobile app.

**Phase 1 done when:** every item under REQUIREMENTS §4.1 is checked.

## Phase 2: Previews, Search, Trash

### 2.1 Thumbnails
- Images/videos: generate a small JPEG (≤320 px) in the browser (canvas / `<video>` frame) at upload time and attach it as the document thumbnail.
- The list loads thumbnails with `downloadMedia({thumb})` and caches them in Dexie.

### 2.2 Previews and streaming
- **Images:** full-screen gallery viewer with next/previous, zoom, and swipe on mobile.
- **Video/audio:** `public/sw.js` intercepts `/stream/<fileId>` requests, maps the HTTP Range to the right chunk and offset, asks the page (via `postMessage`) to fetch that byte range from Telegram with `iterDownload({offset, limit})`, and streams it back. `<video src="/stream/...">` then seeks natively.
- **PDF:** browser's built-in viewer (Blob URL). **Text/code:** first 1 MB in a text viewer.

### 2.3 Search and filters
- Client-side search over the Dexie index (name contains, case-insensitive), across all folders.
- Filter chips: Photos / Videos / Documents / Audio (by MIME type and extension). Chips always search the whole drive.

### 2.4 Favorites, recent, trash
- Favorite: `x.fav` flag. Recent: sort by `ts`.
- Trash: set `x.tr` with a timestamp on the top-level item (its contents are implicitly trashed). Trash view offers restore and delete forever. On app start, anything trashed more than 30 days ago is deleted.

### 2.5 Multi-select + resume
- Checkbox / Shift-click / long-press selection; bulk move, delete, download.
- Resume uploads: each finished chunk is recorded in Dexie, so an interrupted upload continues from the next unfinished chunk (the user re-selects the same file, matched by name + size + lastModified).

**Phase 2 done when:** every item under REQUIREMENTS §4.2 is checked.

## Phase 3: Android App (Capacitor)

Android only; iOS is not a goal.

### Decisions
| Decision | Reason |
|---|---|
| **Capacitor** (not native Kotlin / React Native / Flutter) | Reuses 100% of the web app; Android's WebView is Chrome, so GramJS, IndexedDB and the streaming service worker work unchanged |
| Capacitor **7** | Capacitor 8 needs Node 22; 7 runs on Node 20 and is stable. Upgrade later with `npx cap migrate` |
| `capacitor.config.json` (not `.ts`) | The CLI can't load `.ts` configs with TypeScript 7 |
| **minSdk 29** (Android 10+) | Scoped storage + `MediaStore.Downloads` without legacy code paths |
| One custom plugin (`TeleDriveNativePlugin.java`) | Fewer dependencies than several community plugins, and exactly the behavior we need |
| `allowBackup=false` + data extraction rules | The Telegram session lives in app storage; it must not be copied to cloud backups |

### What the native plugin does
| Feature | How |
|---|---|
| Downloads | `MediaStore.Downloads` → `Downloads/TeleDrive/…`; bytes streamed from JS in 1 MB base64 pieces |
| Open with… / PDFs | Download into the cache, share via `FileProvider`, `ACTION_VIEW` chooser (WebView has no PDF viewer) |
| Share → TeleDrive | `SEND` / `SEND_MULTIPLE` intent filters; JS reads shared files in 512 KB slices (`PhoneFile`), then a folder picker |
| Camera backup | `MediaStore.Files` query for `DCIM/Camera` images/videos; backed-up IDs stored in IndexedDB; runs on open/resume/network change; Wi-Fi-only option |
| Thumbnails for phone files | `ContentResolver.loadThumbnail` |
| Background transfers | Foreground service (`dataSync`) + partial wake lock while the transfer queue is busy; JS keeps running because Capacitor's `KeepRunning` is on |
| Back button | Stack of handlers (preview → dialog → menu → selection → drawer), then history, then minimize |

### Build
`npm run android` (build + sync + open Android Studio) → Run ▶, or `./gradlew assembleDebug` with `JAVA_HOME` set to Android Studio's JBR.

**Phase 3 done when:** the APK installs on your phone, you can log in, browse, upload from the gallery via Share, and the camera backup works.

## Phase 4: Encryption and Polish

### 4.1 End-to-end encryption (optional per drive)
- A password is turned into a key with PBKDF2-SHA256 (600k iterations) using WebCrypto. The salt is stored in the config message.
- Each chunk is encrypted with AES-256-GCM. File content is encrypted in 64 KB blocks, each with its own IV, so streaming and seeking still work.
- File names are encrypted too (the caption stores ciphertext; `x.enc:1`).
- The password is never stored remotely; there's an option to remember it on the device.
- **Warning in the UI:** a lost password means the files can't be recovered.

### 4.2 Remaining features
- **Duplicate detection:** SHA-256 at upload (stored as `h` in the caption); warn if it already exists.
- **Folder upload:** `<input webkitdirectory>` / drag a folder; recreate the structure.
- **ZIP download:** stream with `client-zip` into the File System Access API.
- **Share with a Telegram user:** `messages.forwardMessages` to a picked contact.
- **Multiple drives:** each drive is a separate channel; a drive switcher in the sidebar.
- **Dark/light theme:** Tailwind `dark:` classes; follows the system with a manual override.
- **PWA:** manifest + install prompt.

### 4.3 Deploy the website
- `npm run build` → deploy `dist/` to Cloudflare Pages or GitHub Pages.
- Decide then: build **with** keys (personal) or **without** (users enter their own on the Setup page).

**Phase 4 done when:** every item under REQUIREMENTS §4.4 is checked and the site is live.
